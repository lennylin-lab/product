# 生产计划与排程计划系统需求说明书

## 一、文档目的

本文档用于定义生产计划、排程、执行与状态闭环的需求边界，作为代码实现、测试验收和后续接口设计的统一依据。

## 二、业务背景与目标

当前项目已经具备订单、订单行、生产批次、工序任务、派工与执行事件等核心对象，但历史实现主要集中在单模块能力，存在以下问题：

- 排程曾长期只看机台和班次，缺少模具与协同资源约束，导致结果可执行性不足。
- 任务执行事件可以落日志，但批次、订单行、订单状态没有随之自动闭环。
- 订单状态守卫分散，存在通过普通更新接口旁路修改已投产订单的风险。
- 文档长期停留在骨架层，缺少可验收的功能和边界描述。

本轮需求目标如下：

- 建立从订单到任务的统一状态语义。
- 让排程至少具备机台、模具与换型成本约束。
- 让执行事件能够驱动批次、订单行、订单状态自动刷新。
- 让关键规则具备自动化测试与验收口径。

## 三、适用范围

- 订单与订单行管理。
- 生产批次生成、释放与状态流转。
- 工序任务排程、派工与执行事件。
- 机台、模具及扩展协同资源约束。
- 需求、测试、验收与进度文档。

## 四、核心角色

| 角色         | 关注点                     | 主要操作                                               |
| ------------ | -------------------------- | ------------------------------------------------------ |
| 计划员       | 订单拆解与批次释放         | 维护订单、订单行、批次，确认是否具备进入生产条件       |
| 排程员       | 任务排程与资源匹配         | 选择排程策略，发起单任务或全量排程，关注冲突与延后原因 |
| 车间执行人员 | 任务开始、暂停、恢复、完工 | 通过执行事件推进任务并回写过程状态                     |
| 生产主管     | 进度与异常监控             | 查看批次、订单行、订单状态与排程结果是否一致           |
| 系统管理员   | 资源与基础配置             | 维护资源、日历、状态配置与系统参数                     |

## 五、核心业务对象

| 对象                   | 说明           | 当前实现要点                                                          |
| ---------------------- | -------------- | --------------------------------------------------------------------- |
| `CustomerOrder`        | 客户订单       | 手工状态只允许 `NEW` 与 `CONFIRMED` 间流转，已投产/已完成不可人工修改 |
| `OrderLine`            | 订单行         | 承接订单拆分后的生产需求，并与批次状态联动                            |
| `ProductionBatch`      | 生产批次       | 订单行拆批后的生产载体，可被释放进入生产                              |
| `OperationTask`        | 工序任务       | 排程输入主体，已具备资源需求、换型时间、最早开始时间等字段            |
| `TaskAssignment`       | 任务派工记录   | 承接排程结果与机台绑定关系                                            |
| `Resource` / `Machine` | 生产资源与机台 | 已支持机台日历、默认准备时间、模具兼容关系                            |
| `TaskEvent`            | 任务执行事件   | 已支持开始、暂停、恢复、完工事件记录和状态刷新触发                    |

## 六、目标业务流程

1. 订单录入后进入 `NEW` 状态。
2. 订单确认后进入 `CONFIRMED` 状态，并允许后续拆单、拆批与排程。
3. 订单行生成生产批次，批次释放后形成待排工序任务。
4. 排程服务加载 `READY` 任务、可用机台、班次日历、任务资源需求和机台兼容信息。
5. 排程计算器根据策略选择候选机台，生成 `TaskAssignment` 并更新任务状态。
6. 车间执行人员对任务执行开始、暂停、恢复、完工等操作，系统写入 `TaskEvent`。
7. 任务事件成功后触发状态刷新链路，批次、订单行、订单状态逐级更新。
8. 当所有下游对象完成后，上游对象进入完成状态。

## 七、功能性需求

### 7.1 订单状态守卫

- 系统必须在服务层统一校验订单状态流转。
- `check`、`cancelCheck`、`updateCustomerOrder` 必须复用同一套状态校验逻辑。
- 已投产订单不得被修改为未投产状态。
- 已完成订单不得再被任何普通编辑入口修改。
- 手工可维护状态仅限 `NEW` 和 `CONFIRMED`。

### 7.2 批次与任务准备

- 订单行拆批时必须校验可分配数量，禁止超量拆批。
- 批次释放后，相关工序任务应具备进入排程所需的前提状态。
- 任务对象必须能表达最早开始时间、工序顺序、换型时间和资源需求。

### 7.3 资源约束排程

- 排程必须只处理 `READY` 状态且未存在派工记录的任务。
- 排程必须加载可用机台与机台日历，并对班次开始、班次结束进行时间对齐。
- 排程必须支持任务级资源需求，并在机台选择前校验硬约束。
- 当前版本至少要校验以下约束：
  - 指定机台的强制约束。
  - 指定模具的强制约束。
  - 机台与模具兼容关系。
- 当资源不兼容时，任务不得被错误派到不满足条件的机台。

### 7.4 排程策略

- 系统必须支持 `EARLIEST_START`、`EARLIEST_FINISH`、`DUE_DATE_PRIORITY`、`LOWEST_COST` 四种策略。
- `LOWEST_COST` 不能只是新增枚举，必须基于任务换型时间或机台默认准备时间参与排序。
- 新策略启用后，不得破坏原有 3 种策略的行为与排序基准。

### 7.5 执行事件与状态闭环

- `start`、`pause`、`resume`、`complete` 必须记录任务事件。
- 任务事件成功后，系统必须在同一业务链路内触发状态刷新，而不是依赖控制器手工拼装。
- 状态刷新顺序必须遵循：
  - `PRODUCTION_BATCH`
  - `ORDER_LINE`
  - `CUSTOMER_ORDER`
- 批次状态至少应能根据任务状态进入 `RELEASED`、`IN_PROCESS`、`DONE`。
- 订单行与订单状态必须根据下游批次、订单行的集合状态自动推导。

## 八、非功能需求

### 8.1 一致性

- 关键状态变更必须运行在清晰的事务边界内，避免“任务已完工但订单未刷新”这类部分成功。
- 排程输入必须稳定排序，避免同一输入在无业务变化时产生随机结果。

### 8.2 可解释性

- 排程策略必须可通过参数切换。
- 排程结果应能说明任务为什么被延后，至少能定位是班次约束、机台占用还是资源不兼容。

### 8.3 可测试性

- 订单状态守卫、资源约束排程、最低成本策略、任务事件闭环必须具备自动化测试。
- 新规则必须优先通过服务层测试保护，必要时再补集成测试。

### 8.4 安全与维护性

- 敏感配置不得以明文提交到仓库。
- 状态规则应集中在服务或状态刷新器中，避免散落到控制器和调用方。

## 九、验收标准

### 9.1 功能验收

- 当订单状态为 `IN_PRODUCTION` 或 `DONE` 时，`check`、`cancelCheck`、`updateCustomerOrder` 都会拒绝修改。
- 当任务要求特定模具时，排程不会选择不兼容该模具的机台。
- 当启用 `LOWEST_COST` 策略时，在满足硬约束的前提下优先选择准备成本更低的机台。
- 当任务执行 `start/pause/resume/complete` 成功后，系统会记录事件并触发批次、订单行、订单状态刷新。
- 关键服务测试命令通过：`product-services` 下 planning、execution、demand-service。

- `docs/TODO.md` 反映真实完成项与剩余缺口；本说明书不跟踪未完成项，进度统一以 TODO.md 为准。
