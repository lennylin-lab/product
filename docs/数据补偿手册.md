# 数据补偿手册（三域状态一致性）

> 适用范围：Spring Cloud Alibaba 微服务体系（execution → planning → demand 事件链，ADR-0004）。
> 工具：`scratch/phase6/scripts/validate_data.py`（巡检）、`scratch/phase5/recon.py`（对账/补偿/重放）、
> 各服务 `/internal/<domain>/ops/*` 端点（管理员权限，网关不可达，服务端口直连 + 管理员 token）。

## 1. 一致性模型回顾

- 事件链：execution 命令（start/pause/resume/complete）写 `task_event` + outbox（同事务）→
  `task.status.changed` → planning 消费更新任务状态并按任务聚合批次状态 →
  `batch.progress.changed` → demand 消费维护 `planning_batch_state` 投影并聚合订单行/订单状态。
- 每个服务内置**本域对账定时任务**（默认 60s，`*_RECON_INTERVAL_MS` 可调）：
  漂移写 `ops_audit`（RECON_DRIFT）并自动修复（RECON_HEAL）。
- 跨域不变式由 recon.py 巡检：
  - **X1** planning.production_batch.status == demand.planning_batch_state.status（投影一致性）
  - **X2** execution.task_event 最新目标状态 == planning.operation_task.status（仅 outbox 收敛时判漂移）
  - **X3** order_line.allocated_qty == SUM(production_batch.batch_qty)（拆批预占一致性）
  - **P1/D1/D2** 各服务本域聚合不变式（batch=aggregate(tasks)、line=aggregate(投影)、order=aggregate(lines)）
  - **H** 三域 outbox PENDING/HALTED 计数 + 死信未重放计数

## 2. 巡检（只读）

```bash
python3 scratch/phase6/scripts/validate_data.py     # 行数快照 + 不变式复核 + recon 终局判定
python3 scratch/phase5/recon.py report              # 跨域差异报告（不修改任何状态）
```

`drifts=[]` 即链路健康；任何漂移先看 `check/desc/expected/actual` 定位域与聚合。

## 3. 补偿动作（全部经 ops 端点，服务端 ops_audit 留痕）

```bash
TOKEN=<管理员登录 token>

# 批次状态按任务聚合重算（变更则自动发布 batch.progress.changed 级联下游）
curl -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"batchId":123}' http://127.0.0.1:8104/internal/planning/ops/recompute-batch-status

# 订单行状态按投影批次聚合重算（订单级随之重算）
curl -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"orderLineId":456}' http://127.0.0.1:8103/internal/demand/ops/recompute-line-status

# 订单状态按订单行聚合重算
curl -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"orderId":789}' http://127.0.0.1:8103/internal/demand/ops/recompute-order-status

# 已拆批数量人工修正（幂等设值；用于 Phase 4 拆批"先预占后落批"补偿窗口的对账收敛）
curl -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"orderLineId":456,"newAllocatedQty":30}' http://127.0.0.1:8103/internal/demand/ops/adjust-allocation
```

等价 recon.py 命令：`heal batch|line|order <id>`、`heal allocation <lineId> <qty>`。

## 4. 人工重放（outbox / 死信）

```bash
# 查看待处理行
curl -H "Authorization: Bearer $TOKEN" "http://127.0.0.1:8105/internal/execution/ops/outbox?status=HALTED"
curl -H "Authorization: Bearer $TOKEN" "http://127.0.0.1:8104/internal/planning/ops/health"

# 重放 outbox 事件（新 eventId + 原 correlationId/payload；消费方按 eventId 幂等）
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"outboxId":123}' http://127.0.0.1:8105/internal/execution/ops/replay-outbox

# 重放死信审计行（重投原 exchange/原 routing key；毒消息按设计再次死信，形成新审计行，不丢不吞）
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"auditId":45}' http://127.0.0.1:8105/internal/planning/ops/replay-dlq
```

等价 recon.py 命令：`replay outbox <domain> <id>`、`replay dlq <domain> <id>`。

## 5. 处置决策树

```
validate_data.py / recon.py report
├─ drifts 非空
│   ├─ P1/D1/D2（本域聚合）     -> 通常已被服务内定时对账自动修复（RECON_HEAL）；
│   │                              未修复时用 §3 recompute-* 人工收敛
│   ├─ X1（投影 vs 批次）       -> planning 域 replay-outbox 重放 batch 事件 + recompute-line-status；
│   │                              或 demand 域 recompute-line-status 按投影重算
│   ├─ X2（事件 vs 任务终态）   -> 确认 execution outbox 已收敛（H 检查）后 replay-outbox 重放缺失事件
│   └─ X3（预占数量）           -> 以 planning SUM(batch_qty) 为准，adjust-allocation 幂等设值
└─ H 不健康
    ├─ outbox PENDING 持续增长   -> RabbitMQ 不可用/消费停摆：查中间件，恢复后 relay 自动排空
    ├─ outbox HALTED             -> 重试耗尽：修复根因后 replay-outbox
    └─ 死信未重放                -> 查 dead_letter_audit 失败原因，修复后 replay-dlq
```

约束提醒：ops 端点要求管理员权限（Phase 6 决策，`@ss.hasPermi('*:*:*')`），全部动作 ops_audit 留痕，
可在 `/internal/<domain>/ops/health` 的 recentAudit 中审计。
